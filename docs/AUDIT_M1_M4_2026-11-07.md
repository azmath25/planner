# Dayframe — implementation audit, Milestones M1–M4

**Audited:** 2026-11-07  
**Scope:** `azmath25/planner`, Dayframe Neon project `soft-night-61558675` / database `dayframe`. No Quizer or Mimo code or data.  
**Method:** Read executable frontend/backend sources, SQL migration bodies, test harnesses and CI workflows; queried live Neon migration state, Function deployments and trigger metadata; ran the nonpersistent SQL rehearsal described below. README files and milestone checkpoints were consulted only as a list of claims to verify—not treated as evidence of implementation.

## Executive summary

The application has a functioning authenticated Neon data path for workspaces, tasks, ordered daily pools and fixed-time intervals. Reminder operations and a scheduled browser-push path are deployed. Core security invariants are implemented in API ownership checks and PostgreSQL constraints. **However, M1–M4 are not fully production-accepted:** authenticated Safari use and true two-account/cross-device behavior remain unverified, and no real user device has yet received a proven M4.3 push.

There is **exactly one GitHub branch (`main`)** at audit time. Live Neon reports migrations `0001`–`0010` in order, Function `dayframeapi` deployment **10** and `dayframedue` deployment **2** completed, and an enabled five-minute reminder trigger.

## Findings and risks, ordered by action priority

### A1 — Browser authentication and real users (high)
Neon Auth uses a separate domain from GitHub Pages. A cross-site cookie may be blocked in Safari. The available local preview does not prove real account sessions work. Validate login, refresh, sign-out, role ownership, two separate accounts and real phone/desktop navigation. Do not disable JWT verification to work around Safari. A first-party/same-site auth arrangement may ultimately be necessary.

### A2 — Real push delivery (high; M4.3 acceptance gate)
The scheduled Neon trigger and outbox have been tested, but no actual subscription endpoint belonging to a real consenting browser has been exercised. Test granted/denied notification permission, closed-tab delivery, click reopening, unsubscribing, expiration cleanup and two-account separation. OS/device push availability is not guaranteed merely by an HTTP 201 from a push service.

### A3 — Broader reminder semantics (medium)
Only **one** legacy task-level soft reminder date/time exists. Multiple independent reminders per task, recurring reminders, quiet hours, email, configurable deadline-warning thresholds and complete DST fold/gap handling are not implemented. Treat these as outstanding acceptance relative to the full PRODUCT_PLAN, not features silently completed under M4.3.

### A4 — Architectural and performance debt (medium)
Most UX logic remains in the large imperative `legacy.ts` adapter, despite the React shell. This increases mutation/rerender and integration risk. Incrementally move high-change pages into typed React components and add end-to-end tests; do not replace the UI wholesale or discard its current appearance.

### A5 — Local data versus Neon records (tracked, not a regression)
Daily capacity, timer sessions, Quick Notes and workspace-photo previews remain browser-local. Historical local planned intervals were deliberately not imported to avoid duplicate records. M5 deals with persisted time tracking, and M6 with notes/documents. Users must not mistake browser-local time totals for synchronized history.

### A6 — Trigger endpoint trust and delivery guarantees (medium)
The worker checks Neon's documented trigger-invocation header and named schedule event, but the marker is not itself a cryptographic authentication method. Queue eligibility, destination allowlisting and dedup limit abuse; nevertheless a stronger trigger-only trust boundary should be considered. A crash after Web Push accepted but before receipt persistence can cause retry; this is **at-least-once**, not provably exactly-once. Device notification tags help collapse duplicates.

### A7 — Cost observation (low)
The five-minute scheduled Neon Function runs even when no reminders are due. Monitor actual usage/charges as the project grows rather than assuming background delivery is free. Maintain the small batch and retry caps.

### A8 — User-facing duplicate alert display (fixed during this audit)
Signed-in Home originally rendered an independent "Needs your attention" task-date list below the new inbox, potentially resurfacing acknowledged alerts. The signed-in view was changed to direct users to the actual account-scoped inbox; the demo retains its date-based preview card. The latest React build and M4.3 browser regression both passed after this fix.

## Release decision and next boundary

**M4.3 code and deployment:** implemented; server-level verification passed.  
**M4.3 user acceptance:** still open for real device push, Safari login and real two-account behavior.  
**M1–M4 overall:** materially implemented, but **not fully production-accepted**. No destructive cleanup, data migration, GitHub branch changes, or work on M5 was authorized or attempted in this audit.

Recommended sequence before M5: perform a short real-user device/account acceptance pass for A1–A2, decide whether A3's richer reminder features are required for M4.3 sign-off, and harden any findings. Then explicitly approve M5.1.
